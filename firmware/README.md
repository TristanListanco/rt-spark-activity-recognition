# RT-Spark firmware

Reads the on-board ICM-20608 IMU at 5 Hz, joins Wi-Fi through the on-board RW007 module, and publishes one MQTT message per second in the format of [docs/CONTRACTS.md](../docs/CONTRACTS.md) (section 3). It receives the cloud's prediction back and shows it, with the board's status, on the on-board LCD.

It follows the lab's sequence: initialise the sensor → join Wi-Fi → connect to the MQTT broker → send a reading every second.

## What is in this folder

Only what is specific to this project:

| Path | Contents |
|---|---|
| `applications/` | The application code (below) |
| `.config`, `rtconfig.h` | The RT-Thread configuration, generated by [`tools/firmware_config.py`](../tools/firmware_config.py) |
| `build.sh` | Fetches RT-Thread at a pinned commit, copies the two items above onto its official `stm32f407-rt-spark` board package, downloads the packages and builds |
| `tests/` | Compiles `payload.c` on the host and checks it against the cloud classifier's own code, in both directions |

The rest (the RT-Thread kernel, the STM32 HAL, the RW007, ICM-20608, Paho MQTT and netutils packages) is about 100 MB of upstream code. It is fetched into `firmware/.rtt/` (git-ignored) instead of being copied into this repository.

### Application code

| File | Job |
|---|---|
| `main.c` | Starts the display, IMU and network threads (IMU and network are connected by a message queue); drives the LEDs; polls the buttons |
| `label.c` | Recording labels from the buttons (see below). Command `rec` |
| `imu.c` | Samples the ICM-20608 every 200 ms on a fixed tick grid (±8 g, ±1000 °/s) and converts to g (gravity included) and rad/s; sends one batch of 5 samples per second. Command `imu_read` |
| `net.c` | Joins Wi-Fi (auto-reconnect), syncs the clock with NTP, runs the Paho MQTT client (auto-reconnect), publishes each batch to `activity/rtspark-01/imu`, and subscribes to `activity/rtspark-01/prediction`. Command `app_status` |
| `display.c` | Draws the status screen on the 240x240 LCD twice a second (see below) |
| `clock.c` | NTP time kept with the system tick; `ts` is 0 until the first sync, as the contract allows |
| `payload.c` | Builds the JSON message with 4 decimals (RT-Thread's printf can't print floats), and parses the prediction message |
| `app_config.h` | Device ID, topic, sample rate |
| `secrets.example.h` | Template for `secrets.h` (git-ignored): Wi-Fi and MQTT credentials |

## Build and flash

You need the Arm GCC toolchain. The script finds PlatformIO's GCC 14 automatically (see the repository README for installing it), or set `RTT_EXEC_PATH`.

```bash
cp firmware/applications/secrets.example.h firmware/applications/secrets.h   # then edit it (below)
firmware/build.sh            # build → firmware/out/rtthread.bin
firmware/build.sh flash      # build, then flash through the on-board ST-Link (OpenOCD)
pio device monitor -p /dev/cu.usbmodem* -b 115200                           # serial console
```

`secrets.h` lists the Wi-Fi networks the board knows. Each entry has a name, a password, and **the broker address to use on that network**: the Mac's IP there, or later the Azure VM. At boot the board tries them in order and uses the first one in range, so moving between home and the hotspot doesn't need a reflash:

```c
#define WIFI_NETWORKS \
    {"PLDTHOMEFIBRxxxxx", "home-password", "192.168.1.44"}, /* router's 2.4 GHz name */ \
    {"Tristan’s iPhone 15 Pro Max", "hotspot-password", "172.20.10.2"},
```

The first run downloads RT-Thread (sparse, only this board) and the packages. To reuse an existing RT-Thread checkout, which must be at the pinned commit, set `RTT_DIR=/path/to/rt-thread`.

Wi-Fi requirements: the RW007 joins **2.4 GHz** networks, and the network must hand out **IPv4** addresses (DHCP). IPv6-only networks don't work. A phone hotspot is fine; on an iPhone, turn on *Maximize Compatibility* to force 2.4 GHz.

## On the board

### Screen

```
rtspark-01             13:45:07     device and local time (NTP, UTC+8)
┌──────────────────────────────┐
│           RUNNING            │    the cloud's latest prediction: blue = walking,
│        97% confident         │    orange = running, grey = none in the last 5 s
└──────────────────────────────┘
Wi-Fi  PLDTHOMEFIBR0a448            network joined (green), or "joining..." (red)
IP     192.168.1.48                 the board's address on it
MQTT   online                       green when connected to the broker
Sent   1234   failed 0              messages published (red if any failed)
IMU    |a| 1.01g |w| 0.03           live magnitude: ~1 g and ~0 rad/s when still
Broker 192.168.1.44:1883             the broker for this network
```

The prediction comes back from the classifier on `activity/rtspark-01/prediction` about a second after each message. "WAITING" means none has arrived yet. A grey panel with "no update for N s" means the board or the cloud stopped. The colours are the project's chart palette.

### LEDs

| LED | Meaning |
|---|---|
| Blue blinking once a second | Firmware running |
| Red lit | Not connected to the MQTT broker (yet) |
| Red blinking fast | Startup failed (sensor or memory); see the serial console |

Serial console commands (115200 baud):

- `app_status`: Wi-Fi, IP address, MQTT state, clock, messages sent / skipped / failed, and the last prediction from the cloud
- `imu_read`: the last second of samples in milli-g and milli-rad/s. Lying still, the magnitude should be about 1000 mg (gravity)
- `wifi scan`, `ifconfig`, `ping <host>`: standard RT-Thread network commands

## Recording training data (M7)

The buttons label what you're doing, and every message carries that label until you stop:

| Button | Label | Screen header |
|---|---|---|
| LEFT | walk | REC WALK (blue) |
| RIGHT | run | REC RUN (orange) |
| UP | idle (standing still) | REC IDLE |
| DOWN | stop recording | device name |

On a computer, `tools/record.py --host <broker>` saves every labelled sample to `ml/data/own/*.csv` (git-ignored). Over serial, `rec walk` / `rec stop` does the same without the buttons. If Wi-Fi is gone for 20 s (e.g. you walk out of range of home Wi-Fi), the board tries its other known networks, so a phone hotspot in your pocket takes over.

## Troubleshooting

Problems hit while bringing the board up, and their fixes:

| Symptom | Cause | Fix |
|---|---|---|
| Boots to `msh />` but no `imu`/`net` log lines; `ifconfig` finds no interface | The RW007 driver waits forever at boot for the module's ready pin. The rw007 package's generic pin defaults (e.g. RST = 187, which doesn't exist on this chip) had overridden the board's | The correct RT-Spark pins are set explicitly in `tools/firmware_config.py` (CS 90, INT 107, RST 111) |
| Screen says Wi-Fi connected but **MQTT offline** | The broker isn't at that network's address, usually because the Mac moved to another network (e.g. hotspot → home) or got a new IP | Put the board and the Mac on the same network, and make sure that network's entry in `secrets.h` has the Mac's current IP. The screen shows the network and broker the board is using |
| Home router not found although the Mac is on it | Dual-band routers broadcast a separate 5 GHz name (e.g. `PLDTHOMEFIBR5Gxxxxx`), which the RW007 can't see | Use the 2.4 GHz name (here `PLDTHOMEFIBR0a448`, same suffix without "5G"); `wifi scan` lists it. The board on 2.4 GHz still reaches a Mac on 5 GHz of the same router |
| `not find ap!` when joining | The network isn't visible on 2.4 GHz, or the SSID differs byte for byte | iPhone hotspot: turn on **Maximize Compatibility** (2.4 GHz) and **Allow Others to Join**. iOS names use a curly apostrophe (`Tristan’s`), so copy it exactly. `wifi scan` on the board shows what it can see |
| Board gets an IP but can't reach the broker on the Mac | The hotspot is "IPv6-only preferred" (RFC 8925): macOS skips IPv4 there, while the board still gets IPv4 | Make the Mac take IPv4: `networksetup -setv6LinkLocal Wi-Fi` (undo later with `networksetup -setv6automatic Wi-Fi`). The Mac then gets a `172.20.10.x` address to put in `MQTT_HOST` |
| `Not support Qos0 config, only support Qos1` | RT-Thread's Paho port only publishes with QoS 1 | The firmware uses QoS 1 (contract v0.6) |
| `[E/[RW007]] The wifi Stage 1 status 0 0 0 1` at boot | Logged by the RW007 driver during its normal start-up | Harmless; the module works afterwards |

Verified on the board (October 31, 2026): lying still it reads |a| ≈ 1.01 g. It publishes one message per second with NTP timestamps exactly 1000 ms apart, and reconnects about 6 s after the broker restarts.

## Changing the RT-Thread configuration

The settings live in [`tools/firmware_config.py`](../tools/firmware_config.py): the on-board RW007 and ICM-20608, Paho MQTT in pipe mode, and netutils NTP. To change them, apply the script to a full board package and copy the result back:

```bash
firmware/build.sh                                  # makes sure firmware/.rtt exists
cd firmware/.rtt/rt-thread/bsp/stm32/stm32f407-rt-spark
source ~/.env/env.sh
python ../../../../../../tools/firmware_config.py  # or run `menuconfig` interactively
menuconfig --generate
cp .config rtconfig.h ../../../../../               # back into firmware/
```
